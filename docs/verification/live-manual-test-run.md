# Live manual test run: real Discord, real Slack, local server behind a tunnel, 2026-10-12

Tester: the project owner, driving a real Discord test server, a real Slack channel and the dashboard; Claude Code supplied the test script, read the server logs the owner pasted back, and wrote this report. Code under test: `master` at `4b27ae2` (plus the uncommitted working tree at session start). No application code was changed during the run. No secrets, session ids, CSRF tokens or webhook URLs appear in this report.

## How to read the evidence column

- **Log** means a line from the API's pino output, quoted by event name (`msg`) and ids. Nothing here was inferred from memory.
- **Owner-reported** means the owner told us what Discord, Slack or the dashboard showed. The server log cannot show that.
- **Not evidenced** means the owner confirmed the result but the log lines were not shared with Claude. The result is recorded as passed on the owner's word, and is marked so.

## Design patterns the system uses, and how each one showed up in the run

Paths and line numbers are in `apps/api/src`.

### 1. Ports and adapters (hexagonal)

- **How it is built.** Pure logic lives in `domain/` (for example `domain/retry.ts`, `domain/signature.ts`, `domain/reportState.ts`). Orchestration is in `app/` and talks only to interfaces in `ports/` (`ports/ledger.ts`, `ports/jobs.ts`, `ports/slack.ts`, `ports/discord.ts`, `ports/clock.ts`, `ports/random.ts`). The real implementations sit in `adapters/` (`adapters/pg/pgLedger.ts`, `adapters/pg/pgJobRepository.ts`, `adapters/slackHttp.ts`, `adapters/discordHttp.ts`).
- **Why it mattered here.** Time and randomness are ports: `nextBackoffMs(attempt, base, max, rnd)` takes the random source as an argument (`domain/retry.ts:50-60`), so retry timing is testable. The same code ran live against real Discord and Slack and, in the earlier stub run, against stub servers with no code change.

### 2. Transactional outbox with an idempotent receiver

- **How it is built.** `PgLedger.recordAndEnqueue` opens one checked-out connection, runs `BEGIN`, ensures the guild, then runs the single dedupe statement `INSERT INTO interaction ... ON CONFLICT (id) DO NOTHING RETURNING id` (`adapters/pg/pgLedger.ts:10-16`). No returned row means a duplicate, and it returns `'duplicate'` before writing anything else (`:63-65`). Only the winner inserts the action and the job (`:66-80`) in the same transaction, then `COMMIT`. The interaction token only ever travels as a bind parameter into the job row (`:5`, `:22-24`).
- **Evidence.** 5 concurrent identical deliveries produced 1 winner and 4 `interaction.duplicate` (E2); the duplicate path never created a job. The controller answers (defers) only after the record call returns, so the durable write precedes the ACK.

### 3. Competing consumers with a lease, and a fenced commit

- **How it is built.** The worker claims due jobs with `FOR UPDATE SKIP LOCKED`, stamps `claimed_at` and bumps `attempts`, in one statement (`adapters/pg/pgJobRepository.ts:18-36`). A job whose `claimed_at` is older than the lease is claimable again (`:27`), which is crash recovery. Writing a step's outcome re-checks `status = 'processing' AND claimed_at = $2` under `FOR UPDATE` (`:51-52`), so a worker whose lease expired cannot overwrite the new owner's work.
- **Evidence.** Two workers (pids 12972 and 20808) shared one database and every job still produced exactly one set of attempts (E4).

### 4. Checkpointed, idempotent step pipeline

- **How it is built.** `ReportJobRunner.run` is a fixed pipeline: tag, then mirror, then follow-up, then fallback (`app/reportJobRunner.ts:83-106`). Each step skips itself if its marker is already set (`llm_tag`, `mirror_status`), and writes its marker together with its attempt row through `commitStep`. A retried job never re-posts to Slack or re-calls Gemini. The runner does not throw for a failed call; a throw means the database failed, the job stays `processing`, and the lease recovers it (`:73-75`).
- **Evidence.** In the Slack-rejected run the mirror step ended `fatal`, yet the follow-up step still ran and edited the reply (job `6d147793`). In the dead-token run the mirror was already `sent`, so only the follow-up and fallback were attempted.

### 5. Failure classification plus full-jitter exponential backoff

- **How it is built.** One function decides: `classifyFailure` returns `retryable` only for timeout, network error, 429 and 5xx; everything else, including 401, 404, 408 and 425, is `fatal` (`domain/retry.ts:26-41`). A 429's `Retry-After` wins and is deliberately not capped (`:68-79`). Otherwise the delay is `rnd() * min(maxMs, baseMs * 2 ** attempt)` (`:50-60`). The runner calls `classifyFailure` at each step (`app/reportJobRunner.ts:168, 227, 266`) and nobody re-classifies inline.
- **Evidence.** Slack 404 and Discord 401/404 each produced `outcome:"fatal"` on attempt 1 with no second attempt. The retryable branch (5xx then 200) was not exercised live.

### 6. Graceful degradation with a fallback chain

- **How it is built.** Follow-up fails fatally, so the worker posts to the channel with the bot token (fallback). The fallback body is built by `reportFallbackBody` and, by design, never includes report text for a private report. If the mirror fails, the job finishes `dead` but the reply is still edited, with a notice that the team notification failed (`mirrorFailed` on the `Pass`, `app/reportJobRunner.ts:60-63`).
- **Evidence.** The ⚠️ message "The team notification didn't go through. A server admin can see why on the dashboard." (D2), and the `job.dead` reason text naming Discord and the HTTP status (D8), which is a stored, admin-readable explanation rather than a raw error.

### 7. Request pipeline as ordered guards: verify, then freshness, then parse

- **How it is built.** `InteractionController.handle` runs `verifySignature`, then `isTimestampFresh`, then `parseBody`, and each guard returns before the next runs (`app/interactions.ts:82-113`). Verification is a pure function over `timestamp + rawBody` with explicit hex and length checks and a try/catch that returns false (`domain/signature.ts:29-53`), so malformed input is a 401, not a 500. The freshness check rejects timestamps more than 5 minutes old or more than 60 seconds ahead (`:4-11, 61-72`) and runs only after the signature, because only then is the timestamp trustworthy. `express.raw` is mounted for the interactions route (`http/middleware.ts:107`), so the signed bytes are the bytes checked.
- **Evidence.** Distinct events for each guard: `interaction.signature_rejected`, `interaction.timestamp_rejected`, `interaction.malformed` (400), `interaction.body_rejected` (413).

### 8. Tagged union plus exhaustive routing

- **How it is built.** `classify` turns a validated interaction into a `RouteDecision` union of `ping | command | component | modalSubmit | unsupported` (`domain/router.ts:76-93`). The controller's `switch` over `decision.kind` covers every case (`app/interactions.ts:115-129`), so adding a kind without handling it is a type error. Input is validated at the boundary with zod and unknown fields stripped (`domain/router.ts:30-43`); a PING is answered from its `type` alone, so a PING's missing `member`/`data` is never read.
- **Evidence.** PING handled without a stored row; type 99 handled as `interaction.unsupported` with 200; DM handled without `guild_id`.

### 9. Deadline racing for the 3-second clock

- **How it is built.** `withDeadline(work, ms)` races the work against a timer and always clears the timer (`app/deadline.ts:12-24`). The controller uses it with `recordTimeoutMs` around database work (`app/interactions.ts:248-264`), so a slow or down database yields a private "not logged" reply inside 3 s rather than a Discord timeout. It bounds the wait; it does not cancel the work.
- **Evidence.** Observed response times 1 to 38 ms for commands, 134 ms for the slowest `/report` (first request after idle). The database-down path itself was not run live.

### 10. A state machine derived from events, enforced twice

- **How it is built.** A report's state (`reported`, `acknowledged`, `escalated`) is never stored; it is derived from the action rows (`domain/reportState.ts:38-43`). The allowed transitions are one function (`isAllowed`, `:19-21`), and the buttons shown are exactly the still-allowed actions (`availableActions`, `:24-26`). The database applies the same table: the click is a conditional `INSERT ... SELECT ... WHERE NOT EXISTS (blocking action)` (`adapters/pg/pgReportActionStore.ts:37-42`), preceded by a `SELECT ... FOR UPDATE` on the report's action row so concurrent clicks take turns (`:21-26`). The blocking types come from `blockingActionTypes` (`domain/reportState.ts:49-57`), so SQL and domain cannot drift. The click interaction itself is deduped with the same `ON CONFLICT (id) DO NOTHING` statement (`pgReportActionStore.ts:29-34`).
- **Evidence.** Acknowledge then Escalate both `outcome:applied`; the Acknowledge button was gone after the first click.

### 11. Tenant guard middleware that fails closed with a uniform answer

- **How it is built.** `tenantGuard` parses the `:guildId` path parameter as a snowflake and checks it against the signed-in admin's guilds; a guild that is not theirs, does not exist, or is not even an id all get the same 404 and a `tenant.access_denied` security event with ids only (`http/tenantGuard.ts:28-45`). If the lookup throws, the error handler answers 500, never allowing access. Handlers read the guild through `guildOf(req)`, which throws if the guard was not mounted (`:12-19`). For Discord-side tenancy, the SQL for a button click filters by the signed interaction's guild, never by the `custom_id` (`pgReportActionStore.ts:14`).
- **Evidence.** The 404 probes (F6) were owner-reported; no log lines were shared.

### 12. Rate limiting with a bounded in-memory fixed window

- **How it is built.** `WindowRateLimiter` counts hits per key in a `Map`, counts denied attempts too, and bounds the number of keys by evicting expired and then oldest entries (`domain/windowRateLimiter.ts:25-63`). Time is passed in, so it is deterministic in tests. `AuthService` combines a per-IP-and-email limit with a per-IP limit and takes the longer wait (`app/auth.ts:81-83, 135`), and the route sets `Retry-After` (`http/authRoutes.ts:122`). Behind a proxy, `trust proxy` is set from `TRUST_PROXY_HOPS` (`http/server.ts:91`), which is why the log's `src` showed the real client address through the tunnel.
- **Evidence.** Five failures, then `auth.login.rate_limited` and 429 on the sixth. The limit is per process; a restart clears it (documented limitation).

### 13. Output encoding at each sink, and defence in depth for mentions

- **How it is built.** Slack text is escaped (`& < >`) before it is sent (`domain/mirrorMessage.ts:11-13`, applied at `:25`). Discord replies carry `allowed_mentions` with an empty parse list (`domain/discordResponses.ts:25`), so even a literal `@everyone` in a reply cannot ping. Untrusted text is truncated by code point so an emoji is never split (`domain/discordText.ts:1-5`).
- **Evidence.** The injection test (C5): Slack showed the dangerous tokens as literal text. Slack's `*bold*` rendering is its own markdown, not an escape bypass.

### 14. Structured logging with correlation

- **How it is built.** The controller derives a child logger keyed on `interaction_id` once the body is parsed (`app/interactions.ts:111`), so the HTTP line, the worker's `job.attempt` lines and `job.done`/`job.dead` can be joined by `interaction_id` and `job_id`. Security events carry `logType:"security"`. Login failures return a reference that equals the log `request_id`.
- **Evidence.** Across every log excerpt reviewed in this run, no interaction token, bot token, webhook URL, session id or password appeared.

## Findings from the run

1. **No defects found in the exercised paths.** Every log line matched the designed behaviour.
2. **Process gotchas, not code bugs:** endpoint must be saved after the server is listening; quick-tunnel URLs change on restart; `set-mirror-webhook` takes its secret from the clipboard via stdin only; a webhook placed on a command line ends up in shell history (an exposed webhook should be revoked in Slack and re-created).
3. **Test-plan correction:** "click Acknowledge twice" cannot be done from one message because the button disappears; use two accounts clicking at once instead (E6, not run).
4. **A Discord client limit protects the server-side empty-input check:** a whitespace-only required form field is refused by the Discord client, so only a forged signed request or a unit test reaches that branch.
5. **Known and unchanged:** Slack posts are at-most-once-ish (README, Known limitations); the login throttle is per process; Gemini has still not been exercised against the real service.
