## Setup and deviations

- API: `tsx apps/api/src/index.ts` with throwaway env (fresh Ed25519 keypair, random SESSION_SECRET and WEBHOOK_ENC_KEY, dummy bot token, `SESSION_COOKIE_SECURE=false` for local http only). The web bundle was served from `apps/web/dist/web/browser`.
- Database deviation: the shared Postgres on 5433 needs a password that lives only in `.env`, which I was told not to read. I started my own throwaway Postgres cluster (port 5544, scratchpad data dir) with a scratch database instead. The shared instance on 5433 and the dev/test databases were never touched. The scratch cluster and database were dropped at the end.
- Migrations run with `scripts/migrate.ts`, admins A (alice) and B (bob) seeded with `scripts/seed-admin.ts`, guilds, admin_guild rows and 14 interactions/jobs seeded by SQL. Guild A owned by alice, guild B by bob, plus an unclaimed guild and a "race" guild.
- Downstream: `stub-downstream.mjs` as fake Discord (4010) and fake Slack (4011, mode switched at runtime). The API ran with `DISCORD_API_BASE_URL` and `SLACK_WEBHOOK_URL_PREFIX` pointed at the stubs for the worker scenarios. Dashboard/SSRF tests ran with the default Slack prefix. No traffic went to Discord or Slack.
- A second API instance with `SESSION_COOKIE_SECURE` unset was started briefly to check the default cookie.
- The shared-postgres outage: my scratch Postgres died when the session was interrupted. For roughly an hour the worker logged `worker.tick_failed` / `worker.heartbeat_failed` about 10,600 times each (see finding 4). This is an artifact of my environment but shows a real log-flood behaviour.

## Findings (most severe first)

1. **500 on a crafted log cursor** (medium; availability and information, no tenant leak). Evidence: `GET /api/guilds/<own>/interactions?cursor=<base64url({"t":"2026-13-45T25:61:61.000000Z","i":"100000000000000001"})>` returns 500 `INTERNAL`. Same for `0000-01-01…` and `2026-02-30…`. Server log: `http.unhandled_error` errorCode `22008` "date/time field value out of range" (the log line also echoes the attacker-supplied timestamp string, JSON-escaped). Reproduce: log in, take any valid cursor, replace `t` with a calendar-invalid but regex-valid value. Cause: `CursorBody` in `apps/api/src/domain/logCursor.ts` validates the timestamp by regex only, then `$4::timestamptz` fails in `pgDashboardReader.ts`. Violates "malformed input must not 500". Suggested fix: validate with a real date parse (or catch 22007/22008 and return `invalid_cursor`). Owner: backend.
2. **Duplicate-name cookie "first wins" and an `/api/…` path answered by static** (low, informational). (a) `Cookie: session=bad; session=<valid>` is 401 while the reverse order is 200, so a sibling-subdomain cookie-tossing attacker could shadow a session in plain-name mode; the `__Host-` prefix (default, Secure mode) prevents this in production. (b) `GET /api/%2e%2e/index.html` returns 200 text/html from express.static (it normalises to a file inside dist) instead of the JSON 404, with `Cache-Control: no-cache` rather than `no-store`. No file outside dist is reachable. Optional hardening: have the SPA/static layer skip paths whose raw path starts with `/api` case-insensitively and after decoding. Owner: backend.
3. **attack.mjs sends non-snowflake ids** (tooling, medium for the verification process). The skill's `command()` uses `channel_id:'1'`, user id `'1'`, `application_id:'1'`, `data.id:'1'`; the app rejects them (400), so the "answered within 3000 ms" check fails and the duplicate/concurrent checks are vacuous (400/400). I used a patched copy with 17+ digit ids. Owner: skill maintainer (orchestrator); not application code.
4. **Worker logs about 3 lines per poll while the database is down** (low). During the Postgres outage `worker.tick_failed` and `worker.heartbeat_failed` were logged about 10,600 times each at a 300 ms poll interval, with no backoff or log dedup. At the default 1 s poll this is still about 2 lines/s per failure. The process stayed up and recovered by itself afterwards. Owner: backend (worker loop could back off after consecutive failures).
5. **Login throttle is per process and per IP** (informational). 20 attempts per minute per IP and 5 per IP+email, fixed window. Behind a proxy without `TRUST_PROXY_HOPS` every user shares one IP, so a single attacker can lock out all logins. Operational note for deployment (set `TRUST_PROXY_HOPS`), already supported by config. Owner: deploy notes (main session).
6. **Minor UX/contract nits** (info). `details.fields` shows `"(root)"` for an unknown settings key; `/healthz` has no Cache-Control; valid uppercase-hex signatures are accepted; paths with the `/API` casing are routed case-insensitively to the API. None have security impact.

Not tested / inferred: real Discord and Slack; the Angular UI itself; slackHttp `redirect:'manual'` is inferred from reading `apps/api/src/adapters/httpCall.ts` (not exercised with a redirecting stub); no LLM exists in this build so the LLM-slow scenario does not apply; the exact `500` status from Slack was exercised as 503 (the stub's error class).
